# Python design-pattern decision table

Use rows in order. Start at DP-00, stop when direct code satisfies the pressure, and never stack patterns without separate evidence for each pressure.

## Selection order

1. Name the pressure and its evidence.
2. Try DP-00 direct code.
3. Select one row only if it reduces a demonstrated cost.
4. Define proof and exit before implementation.
5. Hand framework and system concerns to their owning skill.

## Decision table

| ID | Pattern | Pressure/problem | Simplest Python default | Use when | Avoid when | Trade-offs | Misuse / anti-pattern | Clean-code links | Scope | Proof | Exit / reversal | Reference |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| DP-00 | Direct code / no named pattern | No demonstrated recurring design pressure | Function, branch, map, dataclass, module, generator, or composition | One path is clear and change points are few | A repeated pressure is already harming change safety | Lowest ceremony and easiest debugging | Naming a pattern before identifying a problem | [F3](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Local module | Existing tests plus one focused boundary case | Keep direct code until evidence changes | [GoF overview](https://refactoring.guru/design-patterns) |
| DP-01 | Abstract Factory | Related product families must vary together without mixing products | Typed factory function returning a small product bundle | Families have compatibility rules and multiple concrete variants | One product or one stable constructor is enough | Preserves family consistency; adds interfaces and indirection | Factory hierarchy for two constructors with no family invariant | [G23](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md) | Module / subsystem | Parameterized family compatibility tests | Collapse to functions when variants stop multiplying | [Abstract Factory](https://refactoring.guru/design-patterns/abstract-factory) |
| DP-02 | Builder | Construction has many meaningful optional or ordered steps | Keyword-only dataclass or staged functions | Construction rules deserve names, validation, or readable assembly | Data is a plain record with independent fields | Makes invalid construction harder; adds mutable assembly state | Builder mirroring every dataclass field | [G22](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Object construction | Invalid-order and final-object invariant tests | Replace with constructor/dataclass when steps become independent | [Builder](https://refactoring.guru/design-patterns/builder) |
| DP-03 | Factory Method | Concrete implementation owns which product gets created | Function, registry, or constructor injection | Subclass or implementation must preserve creation ownership and polymorphism | Inheritance only delegates to a constructor | Localizes variation; couples creation to hierarchy | Calling every constructor a Factory Method | [G23](../../clean-code/SKILL.md), [G34](../../clean-code/SKILL.md) | Object hierarchy | Contract tests across concrete creators | Remove hierarchy when composition preserves behavior | [Factory Method](https://refactoring.guru/design-patterns/factory-method) |
| DP-04 | Prototype | New objects need configured shape copied from an existing one | `copy`, `deepcopy`, or `dataclasses.replace` with explicit ownership | Copying a configured baseline is clearer than replaying construction | State has external resources or ambiguous deep-copy ownership | Fast reuse; copy semantics and aliasing become part of API | `deepcopy` as a fix for unclear ownership | [G15](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Object graph | Tests prove mutable fields do or do not alias | Replace with explicit factory when copy rules keep expanding | [Prototype](https://refactoring.guru/design-patterns/prototype) |
| DP-05 | Singleton | One shared instance appears necessary | Module state, explicit dependency, or lifecycle-managed object | A genuinely process-wide resource has one owner and lifecycle | Tests, concurrency, configuration, or multiple lifetimes matter | Easy access; hidden dependency, order coupling, and global contention | Singleton used as service locator or cache by reflex | [G23](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md), [G36](../../clean-code/SKILL.md) | Process / lifecycle | Parallel tests and explicit reset/cleanup proof | Replace with DI/module or scoped object when ownership clarifies | [Singleton](https://refactoring.guru/design-patterns/singleton) |
| DP-06 | Adapter | External or legacy interface does not match local contract | Translation function or thin wrapper | Boundary mismatch is stable and should not leak inward | Call site needs only one obvious conversion | Isolates change; can hide lossy conversion and error semantics | Adapter becomes business logic or a second API surface | [G23](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Integration boundary | Contract tests against real-shaped input/output | Delete when upstream contract aligns or wrapper gains domain logic | [Adapter](https://refactoring.guru/design-patterns/adapter) |
| DP-07 | Bridge | Abstraction and implementation vary independently | Composition plus protocol | Two axes will change separately and combinations must stay manageable | Only one axis varies or a direct delegation is readable | Avoids hierarchy multiplication; increases indirection | Bridge before a second axis exists | [G23](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md) | Module / subsystem | Matrix tests for both axes | Collapse to one object when one axis stabilizes | [Bridge](https://refactoring.guru/design-patterns/bridge) |
| DP-08 | Composite | Parts and containers need the same operation contract | Recursive data plus traversal function | Tree consumers should treat leaves and groups uniformly | Tree is shallow or operations differ materially | Uniform callers; recursive failure and ownership semantics | Composite used for arbitrary graphs or to hide cycles | [G22](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Tree / object graph | Leaf, empty, nested, and cycle-boundary tests | Use explicit tree functions when node behavior stays passive | [Composite](https://refactoring.guru/design-patterns/composite) |
| DP-09 | Decorator | Orthogonal behavior must be composed around an unchanged contract | Callable decorator or object wrapper | Logging, retries, authorization, metrics, or caching compose independently | Behavior changes core invariants or order is not explicit | Composable features; ordering, identity, and error flow get harder | Wrapper stack hides latency, state, or exception behavior | [G23](../../clean-code/SKILL.md), [G34](../../clean-code/SKILL.md) | Callable / object boundary | Order, error, and contract-preservation tests | Inline/remove wrapper when only one permanent concern remains | [Decorator](https://refactoring.guru/design-patterns/decorator) |
| DP-10 | Facade | Callers face a complex subsystem and need one safe workflow | Module-level function or small service object | A stable use-case boundary reduces coupling and invalid sequences | Facade merely renames one call or becomes a god object | Easier use and migration; can hide capability and failure detail | Facade accumulates unrelated operations | [G22](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md) | Subsystem boundary | Happy path plus each surfaced failure test | Split or remove when use cases diverge | [Facade](https://refactoring.guru/design-patterns/facade) |
| DP-11 | Flyweight | Many objects repeat large immutable intrinsic state | Interning, `lru_cache`, or shared immutable data | Measured memory pressure justifies sharing and identity is irrelevant | State is mutable, cheap, or lifecycle-sensitive | Lower memory; cache lifetime, eviction, and contention become concerns | Sharing mutable state or optimizing before measurement | [G15](../../clean-code/SKILL.md), [G36](../../clean-code/SKILL.md) | Process / cache | Memory benchmark and mutation-isolation tests | Remove sharing when measurement no longer supports it | [Flyweight](https://refactoring.guru/design-patterns/flyweight) |
| DP-12 | Proxy | Access needs lazy loading, permission, cache, logging, or remote control | Explicit function wrapper or context boundary | Caller contract stays stable while access policy is independent | Proxy hides substantial new domain behavior or remote latency | Centralizes access control; hidden cost and failure modes | Treating remote proxy as local and ignoring retries/timeouts | [G23](../../clean-code/SKILL.md), [G34](../../clean-code/SKILL.md) | Access / integration boundary | Denied, unloaded, timeout, and cache tests | Expose explicit client when proxy semantics become core API | [Proxy](https://refactoring.guru/design-patterns/proxy) |
| DP-13 | Chain of Responsibility | Ordered independent handlers may accept, transform, or pass work | List of callables, guard clauses, or loop | Handler order and fall-through are policy, and handlers stay independent | Every request must hit every step or order is implicit | Extensible pipeline; control flow can become opaque | Long chain used instead of readable local validation | [G22](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | In-process request flow | Order, short-circuit, fall-through, and error tests | Flatten into direct flow when chain order stops changing | [Chain of Responsibility](https://refactoring.guru/design-patterns/chain-of-responsibility) |
| DP-14 | Command | Work must be queued, retried, audited, undone, delayed, or serialized | Callable plus explicit arguments | Work identity and lifecycle matter beyond immediate invocation | One synchronous call has no independent lifetime | Enables queues/history/undo; serialization and idempotency cost | Command object for every function call | [G23](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Task / queue boundary | Replay, duplicate, failure, and serialization tests | Return to direct calls when work has no separate lifecycle | [Command](https://refactoring.guru/design-patterns/command) |
| DP-15 | Iterator | Consumers need traversal without collection representation | Iterator protocol or generator | Traversal state/representation should stay private | A list or one loop is enough | Lazy traversal and composability; lifetime/side effects need clarity | Custom iterator class that only wraps a list | [G31](../../clean-code/SKILL.md), [G34](../../clean-code/SKILL.md) | Collection / stream | Empty, partial, repeat, and close behavior tests | Use direct iteration when representation is already the contract | [Iterator](https://refactoring.guru/design-patterns/iterator) |
| DP-16 | Mediator | Peer objects form too many direct links and coordination rules | Coordinator function or explicit service | Collaboration rules have a real owner and peers should stay independent | Mediator only forwards calls or owns all business logic | Reduces peer coupling; risks a god object and hidden flow | Central event bus used to avoid naming dependencies | [G22](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md) | Collaboration boundary | Interaction matrix and failure propagation tests | Split coordinator or restore direct calls when rules remain local | [Mediator](https://refactoring.guru/design-patterns/mediator) |
| DP-17 | Memento | State must be restored without exposing internal representation | Immutable dataclass snapshot or explicit copy | Undo, checkpoints, or transactions need a stable snapshot boundary | State is huge, external, or snapshot cost is unbounded | Simple restore semantics; memory and copy depth matter | Snapshotting live handles or relying on shallow copies accidentally | [G15](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md) | Object / transaction boundary | Mutate-restore and aliasing tests | Replace with event log or targeted fields when snapshots grow costly | [Memento](https://refactoring.guru/design-patterns/memento) |
| DP-18 | Observer | Multiple independent in-process consumers react to one event | Explicit callback list or direct notifications | Subscribers vary independently and missed coupling is costly | Work is required synchronously or delivery needs broker guarantees | Extensible reactions; unsubscribe, order, errors, duplicates, and backpressure matter | Silent global event bus or observer for required business flow | [G23](../../clean-code/SKILL.md), [G34](../../clean-code/SKILL.md), [G36](../../clean-code/SKILL.md) | In-process event boundary | Subscribe/unsubscribe/order/error/duplicate tests | Use direct calls or domain messaging when guarantees become explicit | [Observer](https://refactoring.guru/design-patterns/observer) |
| DP-19 | State | Object behavior and valid transitions change with lifecycle state | Enum plus transition function | State-specific invariants and transitions are growing | Few states with identical behavior fit data better | Localizes lifecycle rules; adds objects and transition indirection | State classes that only store a label | [G22](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md) | Lifecycle / aggregate | Transition table, invalid transition, and persistence tests | Collapse to enum/data when behavior becomes uniform | [State](https://refactoring.guru/design-patterns/state) |
| DP-20 | Strategy | Several algorithms satisfy one contract and choice varies | Callable, dictionary, or `match` | Algorithms vary independently, are selected at runtime, or need isolated tests | Closed choice is tiny and stable | Makes algorithms replaceable/testable; selection and contract need discipline | Strategy class for a two-branch expression | [G23](../../clean-code/SKILL.md), [G31](../../clean-code/SKILL.md), [G32](../../clean-code/SKILL.md) | Function / service boundary | Contract and representative algorithm tests | Inline or map choices when no independent variation remains | [Strategy](https://refactoring.guru/design-patterns/strategy) |
| DP-21 | Template Method | Workflow skeleton is stable but extension points vary | Composition, hooks, or passed callables | Invariant ordering matters and controlled overrides are valuable | Subclasses violate assumptions or only one implementation exists | Enforces sequence; inheritance and LSP coupling cost flexibility | Base class with empty hooks everywhere | [G23](../../clean-code/SKILL.md), [G34](../../clean-code/SKILL.md) | Inheritance / workflow | Sequence, hook, exception, and subclass contract tests | Replace with composition when extension points multiply | [Template Method](https://refactoring.guru/design-patterns/template-method) |
| DP-22 | Visitor | Many operations vary over a stable set of element types | `match`, `singledispatch`, or element methods | Operations multiply while structure changes rarely | Structure is unstable or operations are few | Adds operations without editing elements; dispatch complexity and coupling grow | Visitor over a tiny tree or as premature double dispatch | [G22](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md) | Stable object graph | Exhaustive type and new-operation tests | Replace with methods/match when structure or operations change often | [Visitor](https://refactoring.guru/design-patterns/visitor) |
| DP-23 | Interpreter | Small language or rule grammar needs repeated evaluation | Parser, AST, `match`, or a standard parser library | Grammar is stable enough to model and expressions need independent evaluation | Input is arbitrary user code or grammar is too large for hand-built objects | Makes grammar changes local; parsing, validation, and runtime safety cost real effort | Treating string formatting or one conditional as a language | [G22](../../clean-code/SKILL.md), [G30](../../clean-code/SKILL.md), [G36](../../clean-code/SKILL.md) | DSL / expression boundary | Parse, precedence, invalid input, and evaluation tests | Replace with direct rules or a parser library when grammar grows | [GoF overview](https://refactoring.guru/design-patterns) |

## Combination rule

Combine patterns only when each pattern answers a separate pressure and each has its own proof. Common combinations such as Adapter + Facade or Command + Memento are valid only when their boundaries remain visible. If the explanation needs more pattern names than pressures, delete patterns first.
