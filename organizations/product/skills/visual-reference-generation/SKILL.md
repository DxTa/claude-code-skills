# Visual reference generation

A reference is a decision aid, not a finished specification or proof that a direction will work.

## Inputs and context

Collect surface and platform, target user/task, desired outcome, content lengths and data volumes, edge states, brand/design constraints, accessibility needs, and the decision the reference should support. Mark known content separately from placeholders.

## Workflow

1. Define one task or outcome per reference and the constraints that make it realistic.
2. Produce genuinely distinct directions rather than cosmetic variations; include primary, empty, loading, error, and narrow/expanded states as relevant.
3. Check hierarchy, interaction affordance, responsive behavior, content density, accessibility, and implementation assumptions.
4. Label each element as direction, decision, or placeholder and gather structured stakeholder feedback.
5. Select or revise a direction, then validate it against user evidence or a prototype before implementation.

## Output and decision record

Return reference brief, alternatives, selected direction, state coverage, known assumptions/placeholders, open questions, expected user/product outcome, and next validation step.

## Uncertainty and failure handling

Do not treat generated imagery as an interaction specification or usability evidence. If content, platform, or accessibility constraints are unknown, expose them and request real examples before approval.

## Routing boundaries

Use this skill only for its stated capability and required context. For adjacent work, select a more specific skill from `skill-index.tsv`; do not infer coverage from this department folder or use this skill to authorize actions outside its scope.

## Never

- Present placeholder copy or imagery as final product content.
- Compare several ideas in one inseparable canvas.
- Skip empty, error, and accessibility states because the happy path looks good.
